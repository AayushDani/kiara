# T07 interfaces — proposed Kiara application contracts

These are Kiara operations, not claimed vendor APIs. TypeScript implementation belongs to the later build. Wire fields are snake_case; API `id` maps explicitly to MongoDB `_id`; record IDs are UUID strings. Tenant identity is injected from authenticated server/session/job scope and never trusted from model arguments. T04 owns final collection validation; T09 owns event envelopes and transitions. T08 owns JCS/SHA256 preimages for review bundles. Config hashes use canonical JSON/SHA256; staged Boolean-only config keys yield the same encoding under sorted compact JSON and JCS. Do not generalize the staging Python serializer to arbitrary Unicode/number document hashes.

## Required persisted shapes

- `harness_versions`: immutable `{_id, tenant_id, version, parent_version_id, config, config_sha256, protected_kernel_version, protected_kernel_sha256, created_from_candidate_id, created_at}`; unique `(tenant_id, version)` and `(tenant_id, config_sha256, protected_kernel_sha256)` if deduplicating identical content. A rejected version may exist as candidate content; only pointer confers champion status.
- `harness_candidates`: immutable `{_id, tenant_id, base_harness_version_id, expected_champion_generation, candidate_harness_version_id, diagnosis_id, patch, base_config_sha256, candidate_config_sha256, protected_kernel_sha256, auto_eligible, created_at}`. `auto_eligible` is server-derived. Lifecycle status is a separate projection of events; mutation of patch/content invalidates the candidate and creates another candidate ID.
- `evaluation_runs`: `{_id, tenant_id, candidate_id, frozen_manifest_id, manifest_sha256, mode, started_at, completed_at, result, case_results, metric_summary, errors, actual_cost, unknown_cost_reservations, latency, runtime_build_sha256, result_artifact_sha256}`. Final result append-only. Completion result is pass/reject/inconclusive; `passed=true` supplied by a caller is never authority.
- `harness_champions`: one mutable pointer `{_id, tenant_id, channel, harness_version_id, config_sha256, generation, auto_promotion_paused, promotion_id, updated_at}`; unique `(tenant_id, channel)`. Generation monotonically increases across promotion and rollback.
- `harness_promotions`: immutable `{_id, tenant_id, action:promote|rollback, from_version_id, to_version_id, from_generation, to_generation, candidate_id, evaluation_id, gate_version, actor_type, actor_id, reason, idempotency_key, created_at}`. Unique `(tenant_id,idempotency_key)`; index `(tenant_id,created_at)`.
- `validation_results` / `repair_attempts`: T04 may embed bounded attempts in run; each receipt binds immutable review_input_hash, validator version, failure code, evidence/claim/clause locators, harness pin, lease fence and run budget counters. No hidden chain of thought.
- `feedback`: T09 canonical type enum, actor/role/time, original text, affected fact/clause/run, disposition and verifying actor. Harness proposal linkage is separate from fact correction or draft-edit linkage.

All private reads include tenant_id. Public shared legal snapshots require explicit shared-resource policy; a legal source reference is not a license to read another tenant's internal document. Use primary/causally consistent reads for immediate post-promotion demo start; no stale secondary pointer cache. Optimizer cannot write evaluation datasets, holdout expectations, result rows, human decisions, or champion collection directly.

## Atomic champion algorithm

1. Outside transaction: construct exact candidate from immutable base; authorize candidate tenant; load trusted finished evaluation and recompute frozen binding/gate. Verify evaluation age ≤24 hours, and verify current operative source status; a stale source blocks promotion even inside this time window. Verify kernel/runtime/catalog match evaluator manifest. Model and kernel rollouts invalidate eval.
2. Transaction with majority write concern and appropriate snapshot reads: recheck candidate/evaluation identities and champion pointer; ensure `auto_promotion_paused=false`; insert target immutable version if not already present and matching hash. Execute update filter `{tenant_id, channel, harness_version_id: expected, generation: expected_generation}` with `$set` target version/hash and `$inc:{generation:1}`. Require modifiedCount=1.
3. Append promotion history, `harness.promoted` and outbox receipt in same transaction. A failure aborts all. Audit/event IDs derived from idempotency key make transaction callback safe if driver retries.
4. Read committed receipt if commit result uncertain. A no-match returns `CHAMPION_CONFLICT`; it never changes base_version in place. Evaluation cannot be reused automatically against a new base. Rollback increments generation even when restoring v1, preventing an old v1→v2 candidate from passing after v1→v2→v1.
5. Revocation/current-law status writes must serialize with promotion using a catalog/kernel revision condition or a CAS-checked policy epoch. Rechecking only outside the transaction leaves a TOCTOU hole. Promotion filter/transaction binds `policy_epoch`, and source/catalog revocation atomically advances that epoch. Final implementation must include this T04/T12 reconciliation field.

## Errors and telemetry

Errors: `PATCH_PATH_FORBIDDEN`, `PATCH_SHAPE`, `PATCH_NOT_MONOTONE`, `BASE_VALUE_MISMATCH`, `CANDIDATE_STALE`, `CHAMPION_CONFLICT`, `TENANT_FORBIDDEN`, `PROTECTED_POLICY_CHANGED`, `SOURCE_NOT_OPERATIVE`, `EVALUATION_BINDING_MISMATCH`, `EVALUATION_INCOMPLETE`, `EVALUATION_REGRESSION`, `BUDGET_EXHAUSTED`, `SEMANTIC_REVIEW_REQUIRED`. Validation failures are data, not retryable transport errors.

Every result carries event_id, workflow_id, run_id, trace_id, tenant_id, base/proposal revision IDs, context/evidence/assessment IDs, harness_version_id/config_sha256, validator version and optional candidate/evaluation/promotion IDs. Technical pane reads Atlas summaries: detected failure, repair receipt, config diff, frozen baseline/candidate metrics, active version/generation and later-event receipt. LangSmith may mirror privacy-filtered traces; it never becomes authorization or promotion state.


## Reset-epoch correction — authoritative addition after T06 re-freeze

`reset_epoch` is trusted runtime/server context from the persistent tenant guard, **never model arguments** and never a patchable config field. It is distinct from policy_epoch (source/kernel revocation) and champion generation (promotion/rollback order). Require tenant_id + reset_epoch on every tenant-private validation, repair, diagnosis, candidate, version, comparison/evaluation, champion, promotion/audit, receipt and run reference. Hydration, tool dispatch and result lookup must match both tenant and epoch even when seed/reset reuses UUIDs. Source snapshots used in tenant scope require matching epoch or an explicit server-approved immutable shared-resource import; old private data is never recovered merely by matching a content hash.

Every candidate write, evaluation-result commit, receipt replay, promotion or rollback transaction must **conditionally CAS/touch the same surviving tenant guard**, matching the pinned reset_epoch, in the same transaction as its effects. A snapshot-only read does not serialize with reset. Promotion additionally compares champion reset_epoch + expected version + generation + policy_epoch. The preflight input hash, result/evaluation manifest hash and idempotency receipt hash include reset_epoch. Every earlier tenant-scoped unique index/receipt identity in this document is refined to include reset_epoch (for example immutable `(tenant_id,reset_epoch,version)` and operation `(tenant_id,reset_epoch,idempotency_key)`); T04 owns final physical encoding. The persistent tenant guard itself is not deleted/recreated by reset.

Reset quiesces model/tool/job/email dispatch, cancels prior in-flight work, then monotonically advances the surviving guard **before** deleting or reseeding fixture data. Preserve unresolved model cost reservations/charges and live-send intents/receipts outside the discarded fixture epoch, or block reset until reconciled. Neither reset nor a fresh evaluation candidate may erase unknown cost/delivery. Late old-epoch results are diagnostic only; they cannot attach to reseeded same-UUID documents, reuse old evaluation passes or promote a champion. A new epoch needs new server-derived records and evaluation bindings. The campaign and child budget caps stay unchanged.

Error `stale_reset_epoch` is a deterministic stale-work result: do not retry the same payload under a newer epoch or silently substitute new IDs. Keep original epoch attribution for diagnostics; authorized new work must be explicitly created from current state. EV-25 specifies racing reset with evaluation completion, receipt reuse and promotion, including preserved unknown charges. Only in-memory fence behavior and schema/hash bindings have been checked here; Atlas reset races remain an implementation acceptance check.
