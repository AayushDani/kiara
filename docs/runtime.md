# Runtime and agent contracts

Kiara uses a durable application harness, not the development agents in Codex. Application agents communicate through persisted, correlated events and versioned receipts in Atlas. MCP is not required for these in-process scoped tools; no MCP interoperability is claimed.

## Roles and flow

1. The authenticated founder or isolated public visitor submits an idempotent event. Its acknowledgment includes event/workflow/reset/context/harness identifiers. Vercel Workflow advances the durable job. Company facts, the actual prior revision, source hashes and harness version are pinned.
2. The drafting agent calls the OpenAI Responses API with strict structured output. It selects scoped company-fact, policy-clause and exact legal-evidence tools. Tool calls retain arguments or hashes, result hashes, call IDs and provider response IDs. The agent can suggest facts or harness changes but cannot verify facts, approve a document, publish, send email or change budgets.
3. The generated output event references an immutable candidate revision, prior revision, input/config/source hashes and provider receipts. Deterministic checks enforce document integrity, known facts, contact values, citation spans actually retrieved, disclosure coverage and preservation of unrelated content. An independent model request checks factual/legal claims against full registered provisions and attributed feedback. Failures retain evidence and enter bounded retrieval/model repair; exhausted or unsupported cases escalate.
4. The improvement proposer is a separate real model call. It sees failure categories and attributed feedback, but cannot see held-out cases. It selects a constrained prompt/retrieval strategy. A separate evaluator executes the production runtime on three frozen cases for both baseline and candidate: the diagnosis and two independently generated unseen company/document cases. Synthetic evaluation inputs are labeled; expected prose is never replayed.
5. Promotion requires actual provider records, candidate success on every case, no regression, measured pass-count or repair-count gain, and at most 25% cost and latency regression. No measurable gain means rejection. Injected tests cannot promote. Frozen source/model/dataset/evaluator hashes and champion compare-and-swap protect the result. New events use the promoted version; in-flight events stay pinned. Rollback retains history.
6. Exact prior/candidate redlines preserve full before/after text and provenance. Founder then lawyer approvals bind the current sealed packet. Fact suggestions need a separate founder verification. Document edits and legal interpretation feedback invalidate stale approvals and revalidate. These attributed corrections independently queue improvement evaluations. Models never supply human approvals.

## Protection and spending

The shared `provider_spend_authorization` MongoDB document covers every visitor and isolated evaluation using the same budget database. It has no visitor TTL or reset generation. Atomic compare-and-swap reservations use integer micro-dollars, at most two simultaneous requests, twenty requests/minute, and a configured total no greater than the user-authorized $50. Unknown charges retain reservations and block dispatch. No SDK automatic retries are enabled. Explicit confirmed token-rate rejections use bounded, audited backoff; billing and uncertain-charge failures do not retry.

Per-run ceilings are $3, twenty-four provider attempts including independent validation and confirmed rate-limit retries, sixteen tool selections, two repairs, 384,000 input and 48,000 output tokens, and a 240-second deadline. Every drafting or repair turn reserves enough input, output, cost and request slots for a complete independent review. Before an exact plan exists, this protects three full checker requests; later repairs use the measured plan plus a 25% input-growth margin. Real acceptance used 57,572 checker input tokens across three full-authority batches, which could not fit alongside 96,874 generation tokens in the previous 120,000-token window. The finite token/request windows now support reviewed repair cycles while the $3 run cap and $50 global authorization remain unchanged. A model proposal reserves at most $0.25; six evaluation trials reserve up to $3 each, within the same global authorization. Adaptation is limited to one campaign at a time per workspace, three daily admissions and recursion depth three. Evaluators do not start nested campaigns. Verified human changes can open a linked child run only after prior accounting settles; immutable parent usage remains visible.

Mutable strategies can choose catalogued factual consistency, minimal edits, legal grounding, feedback treatment and retrieval order. Approval authority, source trust, evaluator criteria, tools, budgets and executable code are protected. The system does not claim unrestricted self-modification.

## Deployment scope

Public live sessions use real server-side OpenAI calls with synthetic demonstration inputs and simulated founder/lawyer roles. Retained source freshness is explicitly a demonstration assumption. Completed paid runs, learning and spend history are not automatically reset or TTL-deleted. A signed visitor cookie selects the workspace; this is not professional identity verification or a real multi-tenant onboarding system.

Private password mode uses separate founder/lawyer credentials and supports explicitly supplied company facts and prior documents via `/api/context`. Live private drafting requires an attributed lawyer check of exact registered official-source bytes. Changed sources require source ingestion/review; the model cannot bless them. Supported legal assessment is the retained California CCPA scope through 2026. Unsupported jurisdictions, missing facts, changed sources and unsupported legal scope escalate. The system is not a general autonomous legal research service.

Email remains preview-only. Internal finalization is not public publication. Local JSON persistence and scripted templating remain explicitly labeled development options.
