# Opt-in attention email and delivery evidence

Product-plan-v2 §§3,6,13,14 require attention delivery with clear scope and owned recovery. `notifications.ts` now implements private enrollment, semantic condition deduplication, one digest per configured local date, quiet-hour deferral, and refs-only durable watch/delivery jobs. In-app required attention remains visible when email is off, acknowledged, unavailable or failed. No notification records work completion or legal clearance.

An operator-managed `KIARA_V2_NOTIFICATION_GRANTS` entry binds one tenant/actor to an exact email, sender, transport mode, application origin and expiry. Live mode names a server credential variable and separately requires `KIARA_ALLOW_LIVE_EMAIL=true`. The user opts in after inspecting that exact configuration hash. Changes to membership or the grant require renewed review. Preview mode records no provider delivery. Settings and delivery views are private to their owner; raw arrays and workflow dispatch details are omitted from the workspace snapshot.

Only a generic link to `/review/attention` is sent. Company names, source text, work titles, dates, counts and recipients of underlying actions remain inside the authenticated application. The review route opens Activity; organization sign-in preserves only this exact allowlisted destination or `/`, signed into the existing state/nonce/PKCE flow. It accepts no arbitrary return URL or consequential action token.

The sending lease and final admission transaction recheck current enrollment, membership, grant, readable source lineage and exact outstanding semantic conditions. A dispatch identity is retained before POST. An expired sending lease, timeout or ambiguous provider result remains unknown and never automatically sends again, including after opt-out/re-enrollment. A late accepted receipt can still attach to the original dispatch identity after recovery. A canceled record with no dispatch may be prepared again after explicit re-enrollment.

States distinguish prepared, sending, provider accepted, provider-delivery verified, unknown, failed, canceled and preview. Readback uses the fixed provider API and checks exact sender, recipient, plain-text body, subject and intent tags, with no extra CC/BCC, HTML body or attachments. Lost receipt attachment requires that same proof. Renewing a grant can reconcile an old attempt when sender, recipient, application origin and transport identity still match; current membership and read access are checked again before and after readback. Renewal does not create permission to repeat an uncertain send. Legacy records without the identity hash remain tied to their exact original grant. It never authorizes another send. Provider delivery is still distinct from the person reading or acting on the underlying work.

Primary API contracts: [Resend send email](https://resend.com/docs/api-reference/emails/send-email), [retrieve email](https://resend.com/docs/api-reference/emails/retrieve-email), [idempotency keys](https://resend.com/docs/dashboard/emails/idempotency-keys). Local attempt fencing does not assume indefinite provider idempotency or claim exactly-once external effects.

Focused injected tests exercise generic payload minimization, exact readback, no-send preview, quiet hours, digest and semantic deduplication, acknowledged/changed conditions, membership changes, opt-out, concurrent dispatch, unknown outcome recovery, late acceptance and canceled-unsent re-enrollment. Authentication tests exercise the allowed review destination and rejected external/ambiguous redirects. No actual email was sent; sender-domain, recipient identity, provider delivery and managed Temporal deployment remain connected-service qualification prerequisites. The preview-only browser path and independent reviewer results are recorded separately when completed.
