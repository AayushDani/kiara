# Kiara v2 hosted release operations

This is the v2 release path. The older [Vercel demo instructions](../vercel-deployment.md) describe a different, anonymous public-demo application and do not qualify a v2 tenant. The current checkout has local and injected-provider evidence; a connected tenant release still requires the checks below.

## Deployment boundaries

- Vercel serves the Next.js web application and bounded Node.js route handlers. Its Functions have finite duration, so the v2 Temporal worker must run as a separate, continuous service. See [Vercel Function limits](https://vercel.com/docs/functions/limitations) and [Render background workers](https://render.com/docs/background-workers).
- Use the reachable Atlas deployment with a separate `kiara_v2` database. The old demo database, schema, and records are not a v2 tenant. Atlas holds normalized v2 records, identity bindings, encrypted original manifests and chunks, and search vectors. Set `MONGODB_DB=kiara_v2`, `KIARA_V2_STORE_MODE=normalized`, `KIARA_ORIGINALS_MODE=mongo_encrypted`, and `KIARA_V2_RETRIEVAL_MODE=atlas` on both web and worker. Pin `KIARA_BUDGET_DB` explicitly and reconcile its existing provider spend before paid v2 calls; it may be a separately managed ledger or the new database after an audited transfer. Back up the 32-byte `KIARA_ORIGINALS_KEY` separately and protect it as recovery material. No production tenant is to be migrated until its exact dry run, source-to-destination tenant mapping, and rollback plan have been reviewed.
- The hosted paid-request gate also requires `KIARA_BUDGET_LEDGER_ANCHOR`, `KIARA_BUDGET_LEDGER_MIN_REQUESTS`, and `KIARA_BUDGET_LEDGER_MIN_SPENT_MICRO` on both web and worker. After selecting the inspected shared Mongo cluster and `KIARA_BUDGET_DB`, run `node --import tsx scripts/v2-budget-ledger-anchor.ts` locally. This read-only command chooses one existing settled charge and prints a SHA-256 anchor bound to its identity, the Mongo host set, database name, and both current request-count and conservatively budgeted-spend floors; it prints no charge ID or credential. Review these values against the existing operator ledger before installing the same values in Vercel and the worker host. A missing row, empty or different ledger, changed cluster/database or floors, absent anchor, or ledger rolled back below either floor blocks hosted reservations and spend status. Settlement and recovery must use that same verified ledger; a drifted target leaves charges unresolved for operator reconciliation. A deliberately transferred ledger needs newly reviewed anchor and floors; a fresh empty ledger is never an implicit reset of the shared cap.
- Temporal holds reference-only workflow history. The application data and source payload remain in MongoDB. The worker connects with TLS and a server-side API key using `KIARA_TEMPORAL_ADDRESS`, `KIARA_TEMPORAL_NAMESPACE`, `KIARA_TEMPORAL_TASK_QUEUE`, and `KIARA_TEMPORAL_API_KEY`. The hosted worker also needs `KIARA_V2_WORKER_TENANTS` and `KIARA_V2_ORCHESTRATION_MODE=temporal`. The web and worker must use the same Atlas database, encryption key, provider settings, and Temporal namespace. [Temporal Cloud credentials](https://docs.temporal.io/cli/cloud) are separate from Vercel deployment credentials.
- Deploy the queued-run evidence hardening on web and worker at the same commit. Runs queued by older builds may fail `EVIDENCE_CHANGED` before provider dispatch because their retained limitations or draft presentation lack the current binding; ask the requester to inspect current records and send a new request. Do not replay an old packet or reset the shared spend ledger to make it pass. Reconcile any already dispatched or unknown provider attempt under its existing run identity before retrying work.
- A continuous worker host is an account and budget choice. [Render currently lists a $7/month 512 MB tier](https://render.com/pricing), while [Fly publishes per-machine prices](https://fly.io/docs/about/pricing/). Neither is provisioned by this repository. `KIARA_V2_WORKER_HOST` records the chosen non-Vercel host for the secret-free preflight; a value does not prove that a worker is running.
- A Render worker created from the public Git repository URL needs manual deployments, even when a CI-based auto-deploy setting is displayed. Auto-deploy after checks requires a connected Git provider. For this Preview, wait for the release branch CI result, then deploy the inspected commit manually. See [Render deploy behavior](https://render.com/docs/deploys).

## Identity and provider configuration

The v2 browser uses OIDC authorization code, state, nonce and S256 PKCE. Configure the exact HTTPS `KIARA_PUBLIC_ORIGIN`, `KIARA_OIDC_ISSUER`, client ID, client secret where the provider requires one, and a 32-character-or-longer `KIARA_SESSION_SECRET`. The IdP subject binds to a tenant and actor in MongoDB `v2_oidc_identities` under a deterministic hashed key. A current normalized membership with the `member` role is required at provisioning and on every authentication check. Binding version or membership changes invalidate signed sessions. `KIARA_OIDC_IDENTITIES` is a local test fixture only when `KIARA_OIDC_IDENTITY_SOURCE=fixture_env`; hosted code rejects that source. Back up and restore the identity collection alongside the normalized tenant. Never restore an older active binding over a later revocation.

Operator identity provisioning needs an exact issuer, subject, tenant, actor, inspected binding version, and current membership. For an isolated test database, set `MONGODB_DB` to a name matching `kiara_synthetic_*` or `kiara_qualification_*`, set `KIARA_V2_RELEASE_SYNTHETIC_DB` to that same name, and set `KIARA_V2_RELEASE_SYNTHETIC_TENANT` to the exact test tenant ID. A synthetic Preview tenant in the actual `kiara_v2` Atlas database instead requires `MONGODB_DB=kiara_v2`, `KIARA_V2_RELEASE_DB=kiara_v2`, no `KIARA_V2_RELEASE_SYNTHETIC_DB`, an Atlas TLS URI targeting `/kiara_v2` or `/`, and an exact `KIARA_V2_RELEASE_SYNTHETIC_TENANT` beginning `synthetic-` or `synthetic_`. Both paths reject a different `--tenant`. Inspect the target tenant and membership before proceeding. `npm run v2:identity -- preview provision --issuer https://id.example.test --subject SYNTHETIC_SUBJECT --tenant SYNTHETIC_TENANT --actor SYNTHETIC_ACTOR --expected-version 0` prints the exact target, current binding, operation, next version, synthetic scope, Mongo store fingerprint, and SHA-256 preview hash. To apply the inspected plan, repeat the same arguments with `apply provision` and `--preview-hash HASH`. For revocation, use `preview revoke` and `apply revoke` with the exact current version, tenant and actor. Apply re-inspects the binding and fails if its version, target, synthetic scope, or store changed. The Mongo write uses compare-and-swap and majority acknowledgement. The CLI never provisions from a browser request. No customer identity binding is authorized by the synthetic Preview path.

For a bounded live delivery test, configure `KIARA_V2_EXECUTION` with one tenant-specific `resend` sender, an exact `allowedRecipients` list containing only a sandbox destination, and a credential environment-variable name. The sender domain and provider account must be configured separately. [Resend test addresses](https://resend.com/changelog/sending-test-emails) support delivered, bounced and complaint exercises. An acceptance response is not delivery: require the provider ID returned in that dispatch, then read back exact sender, recipients, subject, text, absent HTML, an empty [sent-attachment list](https://github.com/resend/resend-openapi/blob/main/resend.yaml), and a delivered event. Resend's retrieve-email response omits send tags and attachments; the immutable local intent retains the tags, while the returned ID binds the original dispatch. A timeout or missing receipt stays uncertain. A later ID with matching payload cannot establish effect identity without independent signed webhook or provider-log correlation, and never authorizes a second POST. Delivery status is point-in-time; a later bounce or complaint requires corrective readback.

## Read-only release preflight

Run `node --import tsx scripts/v2-release-readiness.ts --config-only` with the proposed hosted environment injected. It prints only check codes and booleans. It reads Mongo identity-binding and membership metadata for the selected worker tenants, but does not export tenant payload. The `--config-only` exit status can succeed only after configuration checks pass. Without that flag, the command exits nonzero because connected qualification is still required. Its `releaseQualified` field remains false; no configuration value can turn an injected test into live evidence.

The preflight requires all selected tenants to have a current Mongo identity binding and a configured live email delivery adapter. It requires `KIARA_AUTH_MODE=disabled` on the v2 host and rejects inherited legacy password or demo modes. The legacy `/api/*` route also rejects requests whenever v2 OIDC, normalized storage, or the `kiara_v2` database is selected, before it reads or initializes legacy state. The preflight rejects a fixture identity source, Mongo TLS opt-outs on either data URI, a missing `kiara_v2` database target, missing Atlas index names, missing encryption key, absent OpenAI credential/budget, an implicit or unanchored spend-ledger target, and a missing worker host. The embedding policy is pinned in code to `text-embedding-3-small`; `KIARA_OPENAI_BUDGET_USD` must be positive and within the existing $50 application ceiling. The actual operator spending authorization and ledger reconciliation must also be checked before any paid call. Normalized reads do not create indexes; the first normalized write and explicit index operator establish the required indexes.

The linked Vercel Hobby project `aayushdani01-5976/kiara` currently reports a Ready legacy production deployment from `main@5e4c25d`. Read-only environment inspection found `MONGODB_URI`, `MONGODB_DB`, `OPENAI_API_KEY`, `KIARA_AUTH_MODE`, and legacy `KIARA_*` settings. It did not find v2 settings, OIDC issuer/client, the originals key, or Temporal settings. Names only were inspected; this is not a v2 deployment or a connected readiness pass.

## Connected qualification before promotion

1. Use a new synthetic tenant and reviewed test identities. Verify browser OIDC login, actor mapping, role narrowing, expiry and revocation. Do not copy the earlier remote tenant into local test state.
2. Verify Atlas normalized transactions, named keyword/vector indexes, bounded retrieval and deletion fences. Retain and read back one encrypted original, restore it into an isolated recovery database with the key, and prove revocation still denies access.
3. Start the managed worker on its separate host. Check that an outbox reference reaches Temporal, that a lost acknowledgement replays the same identity, and that stopping/restarting the worker does not duplicate work. Record the worker deployment, task queue and observed status without source text in workflow history.
4. Send only an exact reviewed sandbox email through the selected provider, inspect provider acceptance, and wait for exact delivered readback. Exercise a bounce and an ambiguous outcome without a blind resend. A real customer message, legal notice or fee charge requires separate exact authority and a user-visible preview.
5. Run migration dry run, isolated restore, tombstone/revocation replay, uncertain effect reconciliation, and rollback drills. For the additive legacy archive, `npm run v2:operator -- migrate-check DESTINATION_TENANT SNAPSHOT_PATH DESTINATION_VERSION EXPECTED_LEGACY_TENANT` prints both tenant identities, the exact source hash, counts, and unresolved outcomes without retaining bytes. Review the source and destination mapping even when the IDs differ. Only after that review, `npm run v2:operator -- migrate DESTINATION_TENANT SNAPSHOT_PATH DESTINATION_VERSION EXPECTED_LEGACY_TENANT` can retain the archive. Mixed-tenant legacy workflow or event rows fail before backup retention. This archive import does not cut over or dispatch legacy work. Complete customer-observed first-use value and comparable effort baselines, with independent domain/counsel adjudication where available. Mark A01–A16/J01–J10 as connected only when their own evidence supports that claim.
6. Deploy a Vercel preview from the finished commit and smoke-test it with synthetic credentials. Promote to production only after the above gates and account access are complete. [Vercel CLI deployment steps](https://vercel.com/docs/projects/deploy-from-cli) distinguish preview from production; `VERCEL_OIDC_TOKEN` is a backend federation token, not a CLI deployment token ([Vercel OIDC](https://vercel.com/docs/oidc)).
