# Independent Preview identity and database isolation review · 27 September 2026

Scope: read-only static review of the release worktree at `3897903`, while its owner ran connected Preview checks. This review did not inspect secret values, change deployment settings or issue a legacy login request. The findings below are release blockers until code and connected evidence close them.

1. `src/app/api/[...path]/route.ts` still routes legacy `/api/login` and `/api/workspace` when `KIARA_AUTH_MODE=hosted_password`. `src/data/store.ts` uses the configured `MONGODB_DB` and `readState()` initializes unprefixed legacy collections before reading a workspace. A v2 Preview with `MONGODB_DB=kiara_v2` and inherited legacy password configuration can therefore create/read legacy state in the v2 database outside OIDC tenant binding. `scripts/v2-release-readiness.ts` only excludes `public_demo` and accepts `hosted_password`. The release owner must gate legacy routes off for v2 OIDC or `kiara_v2`, reject the mixed mode in readiness, and read-only inspect the v2 collection inventory for any legacy side effect. Do not drop an unexpected collection without owner/content review. The existing legacy Production deployment is a distinct configuration and should be tested separately.
2. `src/v2/auth.ts` signs subject and binding version in the OIDC session but does not bind the issuer or client ID. After an OIDC provider/client configuration change with the same session signing secret, a cookie issued under the old configuration can authenticate under the new one if that subject resolves to the same tenant, actor and version. Bind exact issuer and client ID to the signed session and check them on every request, or require and enforce signing-key rotation as part of every provider/client change. Existing `tests/v2-auth.test.ts` verifies token issuer/audience before issuing a cookie and membership revocation after issuance, but not a provider/client change after issuance. Add an issued-cookie regression changing only the client ID, then only the issuer, while retaining the secret and mapping.

The release owner was notified during the active Preview run. This note does not establish that a legacy endpoint was exercised or that a cross-issuer cookie was used on the hosted Preview. Connected validation should show legacy routes deny before any legacy store access, confirm no unexpected legacy collections were created, and prove old OIDC cookies fail after provider/client rotation. Until then, a successful authenticated v2 document readback is narrower than complete tenant isolation qualification.

At approximately 23:08 UTC, a separate read-only, host-pinned Atlas inventory of `kiara_v2` showed only `v2_*` collection names, with none of the legacy unprefixed `tenants`, `company_facts`, `workflows`, `events`, `tool_receipts`, `customers` or `demo_workspaces` collections. No document content was read and no database write occurred. This narrows observed damage at that instant; it does not remove the exposed route or prove that every legacy path is unreachable after future configuration changes.

The release owner subsequently pushed `codex/kiara-atlas-production@8606686`. Independent read-only re-review found the legacy route guard runs before login, webhook or store access and covers OIDC, normalized mode and `kiara_v2`; readiness now requires `KIARA_AUTH_MODE=disabled`. The signed OIDC session now includes issuer and client ID, with exact checks on each request. The focused local security suite passed **11/11**. This closes the identified code paths at that commit, subject to branch CI and a redeployed Preview configured with the disabled legacy mode. The actual hosted route denial, current environment and OIDC cookie rotation have not yet been observed in the browser.
