# Provider observation chronology

Provider observations now have separate current, historical and conflicting classifications. Original text, source scope, installation identity and historical audit access remain retained unless access is revoked or deletion is requested. New retrieval, fact confirmation, proposal preparation, model rechecks and final action dispatch require current evidence through the complete source/fact lineage.

The private object register is keyed by provider, installation and scoped object identity. Identical revision/content aliases do not produce duplicate sources or effects. Reusing a provider revision with different material content rejects atomically. Wall-clock occurrence, arrival order and commit SHA sorting do not select truth.

Drive file versions use the provider's numeric monotonic version. Slack message edits use their per-message revision timestamps, compared without floating-point rounding. Opaque GitHub revisions become conflicting when multiple distinct heads are known. A stable, scoped provider read may select its observed current head; ordered reads cannot regress a known newer version. GitHub PR reads compare two complete material representations. A merged PR remains source evidence and never establishes production deployment or automatically confirms company facts.

A full Slack thread is an aggregate, not a single-message revision. Two bounded complete reads must match; the snapshot revision identifies all observed bytes, including deletions. Invalidating a stale aggregate allows a later verified refresh, while withdrawing a message identity prevents late delivery from restoring that message—even if deletion arrived before first content intake. Aggregate admission and read-time ACL eligibility reject snapshots containing known withdrawn message IDs. Attributed deletion matches the exact installation, channel and message revision/content; a withdrawn object removes every matching retained aggregate. Deleting only a historical message revision preserves a newer snapshot containing the newer revision.

Withdrawal never falls back to an older source. There is no implicit undelete or automatic renewal of a withdrawn installation/object identity; an operator restoration workflow remains a limitation. A twice-consistent provider read demonstrates the observed provider state, not a globally atomic snapshot or cryptographic Git ancestry. Provider histories imported without observation metadata remain ineligible for new evidence until reconciled. Retained conflict diagnostics remain visible to authorized reviewers.

When a provider or manually retained source is withdrawn, the same workspace transaction records one private corrective matter per affected prior matter/source. It contains a generic objective, an opaque review reference, an owner task, a durable matter outbox entry and an Activity marker. It carries no withdrawn title, text, proposal body, source lineage or task evidence. The original matter and completed or uncertain effects remain historical; source access rules may hide those records, and the correction never claims to reverse an external effect. A duplicate withdrawal cannot create another corrective matter. The assigned owner must have current business-owner capacity, entity access and authority over the prior matter audience. Otherwise an active entity administrator receives a private operational exception. If neither exists, withdrawal still commits and a durable `source-withdrawal:*` receipt records `owner_unavailable` for operator follow-up.

Current unrestricted entity administrators can inspect only opaque unresolved references with `npm run v2:operator -- withdrawal-status <tenant> <adminActorId>`. After provisioning a current administrator, `withdrawal-retry <tenant> <adminActorId> <EW-reference> <workspaceVersion>` creates the generic private correction from the durable receipt within one transaction; no second webhook is needed. For an administrator-owned correction, `withdrawal-assign <tenant> <adminActorId> <EW-reference> <businessOwnerId> <correctiveMatterVersion> <workspaceVersion>` moves its private audience and pending task to a current entity-scoped business owner. A matter-restricted administrator cannot inventory, retry or assign unrelated exceptions. The former administrator loses matter/Attention visibility. These commands return the opaque reference and corrective matter ID, never the withdrawn source or original matter ID.

If a verified historical effect is unreadable to the new owner, `withdrawal-status` shows a generic count and opaque effect-review hash. An independent unrestricted administrator with current publisher or signing capacity, as appropriate to every affected effect, inspects the retained adapter readback and matching provider receipt, writes a 30–2,000 character review note to a locally retained file, then uses `withdrawal-review <tenant> <adminActorId> <EW-reference> <effectReviewHash> <correctiveMatterVersion> <workspaceVersion> <noteFile>`. The transaction rejects missing or inconsistent readback evidence, changed effect fingerprints and insufficient reviewer authority. It retains the reviewer, membership version, exact effect hash and note hash in the internal receipt, and emits only a generic corrective event/outbox update. The operator must retain the note file under their evidence policy; the workspace does not copy its text. The review claims no new provider delivery or live readback. A later action or reviewer-authority change invalidates the handoff.

The assigned owner can close corrective work through Work → Overview only by a version-bound attestation against exact current, same-audience evidence. Unresolved historical effects block closure. A verified historical effect that has no retained adapter readback and provider receipt remains an open operator exception; this workflow cannot invent delivery evidence. Owner attestation does not alter historical effects or certify legal conclusions. The generic correction is separate from ordinary proposal approval and external-action authorization.

## Qualification

All providers in these tests are injected; there were no live account reads or writes. `tests/v2-source-lifecycle.test.ts` exercises durable intake, late ordered revisions, dependent approval preservation/invalidation, same-revision conflicts, opaque-head resolution, no-fallback withdrawal, deletion-before-intake, complete-thread refresh, stale model packet rejection, keyword/hybrid exclusion, read-time aggregate revocation and scoped physical erasure. `tests/v2-source-review.test.ts` is an independent frozen synthetic corpus checking exact CRLF/UTF-16 excerpts, definition/exception/schedule expansion, adversarial malformed headings and bounded omission notices. It is a parser regression suite, not a legal-quality or model-quality evaluation.

`tests/v2-integrations.test.ts` also covers a signed linked Slack observation followed by deletion, repeat-removal idempotency, a matter-scoped owner's private corrective task and Attention visibility, preserved historical effect states, deletion-after-revocation, direct deletion of closed work without a current proposal, revoked-owner administrator fallback, and a no-current-owner receipt. These are local state and injected-provider checks; connected provider removal and operator recovery remain separate qualification.

Source protocol references: [Drive file version](https://developers.google.com/workspace/drive/api/reference/rest/v3/files), [Slack message edits](https://docs.slack.dev/reference/events/message/message_changed/), [GitHub pull-request reads](https://docs.github.com/en/rest/pulls/pulls). These describe provider identities and reads; they do not establish connected deployment qualification.

TypeScript exited zero (`evidence/source-chronology-typecheck.log`). Root owns the final assembled suite and production-build qualification after that last repair.
