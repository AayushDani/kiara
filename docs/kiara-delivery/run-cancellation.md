# Owner-controlled investigation cancellation

`run.cancel` accepts `runId`, `expectedRecordVersion`, and a bounded reason through the normal authenticated, CSRF-protected, idempotent command route. Only the initiating actor with current membership and access to the conversation and original request can cancel a queued or running investigation. Run views include a monotonically advancing version (older retained rows begin at version1), so stale intent requires a fresh review. This applies to answer, draft, work-plan and accepted-matter preparation runs using the conversation worker.

Cancellation immediately fences further generation, support review and artifact/message attachment. A queued request reaches `canceled` without token counting, provider dispatch or budget reservation. A prepared reservation is recovered as zero and its identity is retired, preventing a delayed original process from reserving it afterward. An already submitted request enters `cancel_requested` while its existing accounting lease remains live. Its response may settle actual usage, but its output cannot be attached and no second stage starts. After the lease expires, unresolved submitted usage becomes unknown and the run reaches `canceled`. Restart and duplicate workers never resubmit that attempt.

The view separates cancellation from accounting: `settling`, `settled`, or `unknown`. Cancellation is not a provider-side abort, refund, deletion, reversal of a completed external action or permission to repeat a charge. A valid response arriving after conservative recovery retains its response ID/hash and observed cost estimate, while both the attempt and global charge remain unknown for explicit operator reconciliation. Ledger errors following a received response cannot masquerade as provider rejections. Query embeddings follow the same accounting boundary, and canceled returned vectors are not reused for generation.

Cancellation audit records inherit source and fact dependencies. Loss of access hides free-text reasons while leaving safe owner status/accounting visible. Source deletion erases the stored reason, audit text and any retained matter preparation objective/tasks. No reason, prompt, answer, provider response or token enters Temporal history: the existing reference-only conversation workflow waits during cancellation accounting and stops after terminal recovery.

Independent root review found two defects during implementation: late valid receipts were lost after unknown-charge recovery, and cancellation reasons lacked derived evidence access controls. Platform review then identified that other ledger outages could still lose receipt metadata. Responses now retain attempt-pinned ID/hash/token usage in a metadata-only transaction before ledger I/O, with output unavailable and status unchanged until settlement. All three findings have explicit regressions. The initial broad AI/hybrid/integration/drafting/cancellation run passed85/85 in13.81seconds (`evidence/run-cancellation-tests.log`). Cancellation and notification checks passed36/36 in6.34seconds (`evidence/run-notification-review-tests.log`). After the final receipt repair, AI and cancellation passed37/37 in6.21seconds, including16 cancellation cases (`evidence/run-cancellation-final-tests.log`). These include actual injected query-embedding cancellation and a ledger outage followed by restart without another provider attempt. All providers and index responses were injected; no paid model call or connected service was used. Final TypeScript exited0.
