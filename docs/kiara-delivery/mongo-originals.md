# MongoDB encrypted originals and retrieval qualification

## Current storage contract

`KIARA_ORIGINALS_MODE=mongo_encrypted` stores new originals in the same `MONGODB_DB` as v2 application records. If `MONGODB_URI` is set and no originals mode is specified, this mode is selected. `KIARA_ORIGINALS_KEY` is a protected, durable 32-byte hex AES-256-GCM key. The key ID is its SHA-256 prefix; loss of the key makes retained bytes unreadable. Keep the key under the deployment secret manager and in a controlled recovery escrow. Key rotation requires an explicit, verified re-encryption procedure before retiring the old key.

The adapter encrypts at the application boundary with a random nonce and the tenant/content/key path as authenticated additional data. `v2_original_chunks` contains ciphertext only. `v2_original_manifests` contains the exact byte count, plaintext and ciphertext hashes, nonce, tag, chunk count and tenant hash. Original identities are content addressed within the tenant and key version. A majority snapshot transaction publishes all chunks and the manifest together. Upload and purge both write `v2_original_fences`, so a concurrent upload cannot resurrect a purged original. Reads validate tenant scope, manifest, ordered chunks, ciphertext hash, authentication tag, plaintext hash and exact byte count. Purge retains a permanent identity fence and verifies that manifest and chunks are gone.

After an operator restores an Atlas backup into a separate `kiara_recovery_*` database, `scripts/v2-original-restore-verify.ts` can read selected original references without writing. Prepare a private JSON manifest with one tenant ID and 2–20 checks of the form `{ "reference": <exact OriginalReference>, "expected": "readable" | "deleted" }`, including at least one of each expectation. Set `MONGODB_DB` to the recovery database, `MONGODB_URI` to its TLS Atlas SRV URI, and `KIARA_ORIGINALS_KEY` to the escrowed key. Run `node --import tsx scripts/v2-original-restore-verify.ts --database kiara_recovery_NAME --source-database kiara_v2 --manifest /secure/path/checks.json`. The verifier requires a distinct recovery database, authenticated readback of retained bytes, and an observed permanent deletion fence. Its output contains only hashes, byte counts and statuses. The operator must separately establish the backup's provenance/time, restored normalized tenant records and identity revocations, access denial, and recovery point/objective; this command alone does not qualify a complete restore.

This is a bounded 20 MB original adapter. It uses 1 MB chunks because MongoDB has a 16 MiB BSON-document ceiling. MongoDB GridFS supports larger files, but [GridFS does not support multi-document transactions](https://www.mongodb.com/docs/manual/core/gridfs/); this adapter needs atomic publication and deletion. Atlas or a replica set with transactions is required. The managed backup and key recovery policy must cover all three collections and the canonical workspace collections together. No claim is made that Atlas snapshots or provider backups are physically erased by an application-level purge.

Legacy `local_encrypted` and `s3_kms` references retain their original adapters. The new Mongo mode does not rewrite immutable workspace references. A **synthetic-tenant-only** cutover is now available through `scripts/v2-original-cutover.ts`. It requires `KIARA_ORIGINAL_CUTOVER_TENANT=synthetic-…` matching the command tenant and an isolated `MONGODB_DB` named `kiara_qualification_*` or `kiara_synthetic_*`. An S3 candidate additionally requires a `kiara-synthetic-*` bucket matched by `KIARA_ORIGINAL_CUTOVER_S3_BUCKET`. These guards are checked before source bytes are read.

Run `node --import tsx scripts/v2-original-cutover.ts preview <synthetic-tenant>` and inspect the full JSON: workspace version/hash, every legacy object ID and reference location, exact local file or versioned S3 URI, byte count, SHA-256, Mongo destination manifest ID, purge target, total count/bytes and preview hash. Preview reads each old object and verifies exact bytes without writing. Run `node --import tsx scripts/v2-original-cutover.ts apply <synthetic-tenant> <reviewed-preview-hash>` only for that reviewed manifest. Apply re-verifies each source, copies to Mongo, verifies exact readback, checks the unchanged workspace hash, and publishes all old-to-new aliases in one majority transaction before attempting the reviewed old-version purge. A partial old purge is reported by hash and can be resumed with the same preview hash. Reads of legacy references for that exact synthetic tenant follow the Mongo alias after activation. No configured remote tenant original was read, copied or deleted during this implementation.

**Retention limit:** Alias-target Mongo bytes remain held after a legacy source deletion. A target can be shared by two old aliases or by a native Mongo reference; deleting either reference must not erase those bytes. Both legacy and native purge now fail closed with `ORIGINAL_ALIAS_TARGET_HELD` when an alias points at the target. Alias activation and target purge write the same permanent fence inside their transactions, so a concurrent activation cannot publish a dangling alias after purge commits. The deletion job remains unresolved until a separately reviewed exact holder manifest and target garbage-collection path are qualified. Host-managed backups need their own expiry/erasure verification. The original alias read/purge patch was initially rejected by automatic approval review for being broader than the synthetic authorization; the implemented cutover is explicitly limited to the named synthetic tenant and isolated database.

## Hybrid search and cost boundary

The existing `v2_search_chunks` collection holds text and embeddings as derived, rebuildable Mongo data. Atlas keyword and vector indexes return IDs only; the service derives allowed IDs from live membership, source lineage and legal-source eligibility before searching, then hydrates source text from the canonical workspace after a second authority check. Exact agreement inventory enumeration remains separate from top-k search. Staged or unreviewed legal sources are excluded before indexing or query embedding. The configured `text-embedding-3-small` policy uses 1536 dimensions and the documented [standard $0.02 per million input tokens](https://developers.openai.com/api/docs/models/text-embedding-3-small); its [input limit is 8192 tokens](https://developers.openai.com/api/docs/guides/embeddings). Existing spend admission and unknown-outcome reconciliation remain in force.

MongoDB lists an M10 base at $0.08/hour and separate S20 search at roughly $0.12–0.13/hour per node on its [pricing page](https://www.mongodb.com/pricing). [Dedicated search requires at least two search nodes](https://www.mongodb.com/docs/atlas/billing/search-node/). Cloud, region, backup, egress, chosen node and provisioned time change the actual bill; an S10 search tier may be available for a smaller trial. No paid cluster was provisioned for this qualification. The team needs a budget cap and selected Atlas region/tier before creating or upgrading a cluster.

## Evidence and remaining release gate

An isolated loopback MongoDB 8.0.32 replica test used generated synthetic records and a generated database. Nine integration tests passed, including normalized store migration and index fencing, a 17 MB encrypted original readback after client restart, duplicate retain, wrong-tenant denial, verified purge and permanent reuse fence. A synthetic local-original cutover exercised preview-hash rejection, exact readback, alias routing, old-file purge and replay. A shared-target regression used two aliases plus a native Mongo holder and confirmed that neither a legacy-source deletion nor a native-source deletion removed the target. A concurrent purge/activation test confirmed that the deleted target could not gain a late alias. Another test rejected a traversal-shaped local key and a non-synthetic S3 bucket before source access. The test dropped only its generated database. This does not verify managed Atlas failover, Atlas keyword/vector index readiness, paid embedding requests, server restart, backup restore or production tenant cutover. Those need a configured sandbox namespace and operator-observed recovery drill before a live release claim.
