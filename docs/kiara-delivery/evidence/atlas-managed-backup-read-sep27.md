## Synthetic managed restore operator sequence

Use `scripts/v2-managed-backup-drill.ts` from a non-hosted operator process with the inspected Atlas `MONGODB_URI`, `MONGODB_DB=kiara_v2`, and no production worker or hosted runtime flags. The script pins the inspected Atlas host set, creates a random `kiara_recovery_*` database and synthetic tenant, and writes a private mode-0600 manifest at the absolute path supplied. This file contains the generated original-encryption key and exact expected state. Store it outside the repository, keep it for verification, and destroy it under the applicable recovery-key procedure after the drill. The generated key is **not** evidence that the production key is escrowed.

1. Run `node --import tsx scripts/v2-managed-backup-drill.ts --seed /secure/absolute/path/managed-recovery.json`. Record the printed generated source database, hashes, and UTC completion time. A successful seed checks retained and deleted original bytes, normalized state, membership revocation and identity binding against that source database. It is not a snapshot check.
2. Wait for a **scheduled** Atlas snapshot strictly after seed completion. In Atlas Backup, record the snapshot ID, UTC snapshot time, source cluster, and selected source database. Confirm that the snapshot contains the generated database. Do not infer this from the backup schedule alone. If the generated database is absent, do not start a restore.
3. Inspect the restore form and select **Restore database(s)/collection(s)**, choose **only** the exact generated source database, and select **Create as new** into a new `kiara_recovery_*` database. Review the summary for exact source/target, snapshot ID and scope before submitting. Do not select `kiara_v2`, overwrite an existing database, or use **Restore entire snapshot** on the active cluster. Record the Atlas restore job ID, start/finish UTC times, target name and any billed transfer estimate or actual charge. A snapshot-only inspection is insufficient to establish the restored database name.
4. After Atlas reports the job complete, run `node --import tsx scripts/v2-managed-backup-drill.ts --verify /secure/absolute/path/managed-recovery.json kiara_recovery_RESTORED_NAME` with the exact new database name. The script requires the copied random marker and checks selected encrypted original bytes, permanent deletion fence, normalized state hash, active/revoked access, tombstone and receipt. It records the candidate target in the private manifest before checking so that a failed verification has a bounded cleanup path. The script does **not** prove the Atlas job provenance; correlate its output with the recorded job ID and snapshot time. For this controlled drill, treat restore start as the simulated failure point: measure snapshot age then as the RPO interval and time from restore start to successful verification as RTO. Report these observed intervals and any target thresholds separately; they do not establish incident-wide production recovery.
5. Once evidence is captured and no retry needs the generated data, clean the source and restored generated databases individually: `node --import tsx scripts/v2-managed-backup-drill.ts --cleanup /secure/absolute/path/managed-recovery.json EXACT_DATABASE`. If verification failed, use the same command with `--abandon` only for a manifest-bound source or candidate restored database. Cleanup checks the exact marker, originating process, allowed collections and synthetic tenant ownership before dropping that database. Confirm both cleanup receipts. Atlas backup copies can outlive live-database cleanup; verify their expiry through Atlas retention evidence later.

The operator must still qualify production key escrow, tenant migration with actual credentials, access denial through the hosted app, Temporal replay, legal-source governance and customer evidence. A successful synthetic managed restore would prove only the selected recovery path and measured timing for this cluster and snapshot.
