# Isolated original target-binding regression — 28 September 2026

Two fresh MongoDB Community 8.0.32 loopback replica sets ran at `127.0.0.1:27931` (`kiaraQualification`) and `127.0.0.1:27932` (`kiaraQualificationSecond`). The opt-in `tests/v2-mongo.integration.ts` suite used one generated `kiara_qualification_<random>` database name on both. It copied only the generated synthetic tenant's workspace, original and alias records between the two targets. No Atlas, customer tenant or provider call was used.

The original cutover preview for the first target had a different hash from the identical workspace/source preview on the second target. Applying the first plan to the second returned `ORIGINAL_CUTOVER_PREVIEW_CHANGED`, leaving the legacy bytes present and no cutover manifest. After the first target's successful cutover, replaying its cloned manifest on the second returned `ORIGINAL_CUTOVER_TARGET_CHANGED`. The alias-target reconciliation similarly rejected the other target's plan before deleting bytes, and rejected a cloned completed receipt on replay. The unchanged-target apply and replay still succeeded.

Command: `KIARA_QUALIFICATION_MONGO_URI='mongodb://127.0.0.1:27931/?replicaSet=kiaraQualification' KIARA_QUALIFICATION_SECONDARY_MONGO_URI='mongodb://127.0.0.1:27932/?replicaSet=kiaraQualificationSecond' node --import tsx --test tests/v2-mongo.integration.ts`. Result: **11/11 passed**, Node v26.7.0; both generated databases were dropped. `npx tsc --noEmit --incremental false` passed. Both temporary MongoDB processes were stopped and their generated `/private/tmp/kiara-recovery-targets.BUMy1s` directories were removed. This is local qualification; it does not prove Atlas migration, managed backup restore or production recovery.
