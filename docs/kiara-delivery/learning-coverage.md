# Executable procedure learning and maintained coverage

Product-plan v2 §§7, 8, 9, 12, 13 and 16 require inspectable lessons, current sources, scoped authority and a measurable later effect. This wave provides one finite deterministic procedure and source/coverage maintenance. It does not claim autonomous legal expertise, broad learned drafting quality, external attorney certification, or model evaluation.

## Real procedure comparison and effect

A lesson remains attributed prose unless `learning.propose` selects the catalogued `release_evidence_before_live_claim` procedure. The executable implementation is fixed server code; candidate text cannot rewrite it or weaken authentication, approvals, budgets or execution boundaries. It applies only to the exact visibility scope of the originating matter. A company-wide/team lesson is not inferred from private precedent.

The selected procedure checks confirmed facts named `deployment` or `production_deployment` when their practice is `live`. Such a claim requires a current confirmed `production_release_verified=true` fact, also labeled live, with an active authorized source citation. The system is checking an attributed evidence requirement, not independently establishing that a production deployment actually happened. Planned practice never becomes live merely because a PR or discussion arrived.

`learning.run_evaluation` requires a distinct authenticated evaluator and current candidate version. It accepts no tests or pass booleans from the caller. The evaluator executes baseline and candidate code on a frozen origin input and the server-owned suite's explicit near-miss and holdout cases: planned work, valid release confirmation, merged-only evidence, stale/revoked evidence, planned release and unauthorized evidence. The suite version, corpus hash, actual baseline/candidate outputs, failures, evaluator membership version and immutable receipt are retained. These are bounded deterministic regression fixtures; they are not a secret independent legal corpus or measured model performance.

Promotion requires zero candidate failures, an actual reduction from baseline failures, current policy baseline, the stored immutable execution receipt, current independent evaluator authority and a separate responsible owner. Manually recorded passing tests cannot promote executable behavior. The active rule has an owner review deadline and can be renewed only against its unchanged passing suite and exact evaluation hash.

Later matter preparation evaluates the promoted procedure against current facts. It preserves settled current facts, adds an explicit evidence blocker when necessary, and prevents proposal decisions while the requirement is unmet. The execution broker also evaluates the current rule immediately before dispatch. Source and owner validity are rechecked, and expired policy review cannot silently remove a safeguard. Current release confirmation clears the evidence blocker after the proposal is rebuilt; business/legal/external-action decisions remain separate.

Rollback marks the lesson inactive, increments the policy version monotonically, identifies matters where it was applied, and invalidates affected current proposals for review. Earlier source assertions, evaluation receipts and action effects remain retained. A database rollback never undoes an external effect.

## Legal source and coverage lifecycle

`coverage.source.add` links a retained source to an HTTPS source URL, domain, jurisdiction, authority type and publication/effective dates. It does not fetch or certify that URL. A named legal reviewer uses `coverage.source.verify` to bind review evidence, the exact source version/hash and a review deadline. Upcoming or expired effective periods remain ineligible for current coverage.

A business owner defines coverage from matching source authorities and their existing visibility scope. A legal reviewer records qualification evidence, limitations and expiry with `coverage.review`. The result explicitly identifies a named reviewer attestation, or fictional local attestation when using demonstration identities. No matter approval is created by a coverage review.

Coverage becomes stale at read time when source, authority review version, reviewer membership, effective dates or review deadlines change. Renewing source verification alone does not renew an older coverage decision. Explicit unavailability remains visible as unsupported coverage. Authorized retrieval carries coverage status and limitations into model requests; it rechecks that status before dispatch and answer attachment. Revoked source content and derived coverage remain denied through the same authoritative lineage rules.

`tests/v2-learning-coverage.test.ts` verifies executed comparison, actual later blocking/clearing behavior, planned-versus-live separation, no duplicated active rule without measured improvement, evaluator revocation, owner-review expiry/renewal, scoped isolation, monotonic rollback and affected work, exact source/coverage review versions, and dynamic staleness. `tests/v2-platform.test.ts` separately proves manual reported tests cannot qualify promotion. The benchmark and service tests are local deterministic execution, with no paid model or external effect.

Remaining work includes general configurable legal playbooks and their independent expert evaluation, broader frozen model/retrieval benchmarks with protected holdout custody, controlled model-strategy shadow rollout, customer-specific recurrence/effort measurement, legally maintained real source collections, and operational professional qualification verification. Revocation safely denies derived content; a complete redacted control-plane recovery UI and physical deletion of historical evaluation payloads still require the broader retention workstream.
